# Execute Plan

Execute a verified implementation plan (generated by `eng-plan`) ticket by ticket, with strict step-by-step validation.

## Execution Rules & Discipline

- **Ticket-by-Ticket**: Execute vertical slice tickets in blocking-edge order (a ticket runs only when everything it declares `Blocked by` is done). Within a ticket, apply its steps in order. Do not skip steps.
- **Slice Integrity**: Finish every layer a ticket declares (frontend, backend, data, tests, acceptance) within that ticket. "Backend done, UI deferred to a later ticket" is a plan defect: halt, fix the plan, then continue.
- **Incremental Verification**: After each step, run its `VALIDATE` command immediately. Fix errors before moving on.
- **Minimal Diff**: Make only the changes the ticket specifies. Avoid unsolicited refactorings, style churn, or scope creep.
- **Preserve Existing Patterns**: Follow the naming, error handling, and formatting conventions the ticket references.

---

## Process

### 1. Load and Verify Plan
1. Read `specs/<feature>/plan.md` and every ticket under `specs/<feature>/tickets/`.
2. Build the blocking-edge graph; confirm it is acyclic. Validate that all target files are understood before touching code.

### 2. Ticket Execution (blocking-edge order)
For each ticket whose blockers are complete:
1. **Prepare**: Read the ticket's story, layers, and referenced pattern files.
2. **Implement**: Apply the ticket's steps (ACTION / TARGET / OBJECTIVE / PATTERN / VALIDATE).
3. **Verify**: Run each step's `VALIDATE` command immediately.
4. **Accept**: Walk the ticket's acceptance criteria exactly as written; the slice must be demonstrable against its user story.
5. **Log Progress**: Check off the ticket and record its state in `.scratch/<pipeline>-state.json`.

### 3. Full Suite Validation
After all tickets pass:
1. Run linting / type checking across affected packages.
2. Run full unit and integration test suites.
3. Execute the plan's manual verification checklist.

### 4. Post-Execution Report
Save the summary to `specs/<feature>/execution-report.md`:
- Tickets completed, in order, with their acceptance results.
- Files modified/created.
- Validation command outputs and test results.
- Unresolved edge cases or follow-up recommendations.

---

## Checkable Completion Criteria

- [ ] All tickets executed in blocking-edge order; every ticket's declared layers completed within it.
- [ ] Every step passed its local validation; the blocking-edge graph stayed acyclic.
- [ ] Each ticket's acceptance criteria walked as written and demoed against its user story.
- [ ] Full project test suite and type checks passed with 0 errors.
- [ ] Execution report saved to `specs/<feature>/execution-report.md`.
- [ ] Execution record appended per `templates/execution-record.md` (executor, skill, version, permissions, steps, results, risk, report), values copied from generated manifests.
